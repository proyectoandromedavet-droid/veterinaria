4. PLAN DETALLADO POR PRIORIDAD
================================================================

PRIORIDAD 1
Refresh token por cookie httpOnly. Eliminar dependencia obligatoria del body. Reenviar `X-JTI`. Corregir logout/logoutAll.

Hallazgo confirmado:
- `services/auth/src/routes/auth.routes.js` exige `body('refreshToken').notEmpty()`
- `services/auth/src/controllers/auth.controller.js` ya acepta cookie `refreshToken`, pero queda bloqueado por el validator de ruta
- `gateway/src/routes/proxy.js` no reenvia `X-JTI`
- `logout` usa `req.user.jti`, por lo tanto hoy puede revocar de forma parcial o nula
- frontend ya llama `POST /auth/refresh` con body vacio y `withCredentials: true`

Correccion objetivo:
- `POST /auth/refresh` debe funcionar con cookie httpOnly como camino canonico
- `refreshToken` en body debe quedar opcional y solo por compatibilidad transitoria
- gateway debe reenviar `X-JTI` desde el access token validado
- `logout` debe revocar exactamente la sesion actual
- `logoutAll` debe operar con `userId` real y no depender del body
- OpenAPI de auth y gateway deben reflejar el nuevo contrato

Cambios puntuales planificados:
- quitar `body('refreshToken').notEmpty()` de la ruta
- mantener en controller el orden actual: cookie primero, body como fallback temporal
- agregar `proxyReq.setHeader('X-JTI', req.user.jti || '')`
- revisar `authMiddleware` para confirmar que `req.user.jti` llegue desde el JWT validado
- actualizar documentación que hoy sigue marcando `refreshToken` como required
- no tocar 2FA en esta fase

Resultado esperado:
- login y refresh funcionan con cookie httpOnly
- no aparece `Validation failed` por faltar `refreshToken` en body
- `logout` y `logoutAll` limpian cookie y revocan sesion real

Dependencias:
- ninguna de DB adicional; `sessions` y `sp_revoke_user_sessions` existen en AWS RDS

PRIORIDAD 2
Corregir CORS y dejar de confiar headers de tenant/org desde browser.

Hallazgo confirmado:
- `gateway/src/middleware/cors.js` usa `ALLOWED_ORIGINS`
- `.env.production.example` usa `CORS_ORIGINS`
- `allowedHeaders` actuales: `Content-Type`, `Authorization`, `X-API-Key`, `X-Branch-Id`, `X-Request-Id`
- falta `X-CSRF-Token`
- no debe aceptarse `X-Org-Id` ni `X-Tenant-Id` desde browser como fuente de autoridad

Correccion objetivo:
- definir una sola variable canonica para origins: `ALLOWED_ORIGINS`
- soportar `CORS_ORIGINS` solo como fallback transitorio si se necesita migracion gradual
- permitir `X-CSRF-Token`, `X-Request-Id`, `X-Branch-Id`
- no exponer `X-Org-Id` ni `X-Tenant-Id` en CORS del browser
- documentar que `orgId` y `tenant` derivan del token/subdominio/gateway, no del cliente

Cambios puntuales planificados:
- unificar carga de origins en middleware y ejemplos de entorno
- ampliar allowlist de CORS sin agregar headers sensibles
- revisar preflight OPTIONS
- revisar si frontend realmente necesita `X-Branch-Id`; si no, idealmente dejar que el gateway derive branch del JWT

Resultado esperado:
- desaparecen fallos de preflight por `X-CSRF-Token`, `X-Request-Id`, `X-Branch-Id`
- no se habilita spoofing de `X-Org-Id`/`X-Tenant-Id`

PRIORIDAD 3
Corregir `subdomainMiddleware` y limpiar headers peligrosos antes del proxy.

Hallazgo confirmado:
- `gateway/src/middleware/subdomain.js` llama auth con `X-Internal-Token`
- auth exige `requireInternalSig`
- `gateway/src/routes/proxy.js` toma `x-branch-id` del request browser como fallback
- gateway hoy reinyecta `X-Forwarded-For` y headers internos sin limpiar primero headers entrantes peligrosos

Correccion objetivo:
- reemplazar `X-Internal-Token` por `X-Internal-Sig`
- firmar la llamada gateway -> auth para resolver slug
- eliminar/ignorar headers sensibles entrantes desde browser:
  - `X-User-*`
  - `X-Org-Id`
  - `X-Branch-Id` como autoridad de seguridad
  - `X-Internal-Sig`
  - `X-Forwarded-*`

Cambios puntuales planificados:
- refactor de `resolveSlug()` para usar `signRequest(...)`
- antes del proxy, clonar/sanear headers y sobrescribir siempre los internos
- evitar fallback `req.headers['x-branch-id']` en el header interno hacia downstream

Resultado esperado:
- tenant por subdominio vuelve a funcionar con el mecanismo zero-trust real
- browser no puede inyectar identidad ni contexto interno

- notifications no usa columnas inexistentes

- el servicio exige HMAC interno o usa `buildApp`

Prioridad 5 aprobada cuando:
- `/ai/*` no queda expuesto si `AI_ENABLED=false`

Prioridad 6 aprobada cuando:
- reports no ejecuta procedures/vistas/tablas ausentes
- los endpoints deshabilitados fallan de forma explicita y controlada, no con 500 generico

- existe matriz canonica de columnas
