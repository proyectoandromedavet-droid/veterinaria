================================================================
1. RESUMEN EJECUTIVO
================================================================

Estado general:
- El proyecto implementa una arquitectura de gateway + microservicios + frontend Vue + MySQL + Redis + WebSocket.
- El diseño base de seguridad es razonable: JWT RS256, refresh token rotativo, Redis para revocacion/rate limit/cache, HMAC interno entre gateway y servicios, RBAC por permisos, hardening HTTP con Helmet/HPP/sanitizacion.
- La implementacion real tiene desalineaciones importantes entre frontend, gateway, OpenAPI, CORS, servicios y esquema SQL.
- Hay varias rutas y servicios que parecen endurecidos en el diseño pero no estan alineados entre si o con el esquema base.

Conclusion ejecutiva:
- El sistema NO esta listo para produccion sin una fase previa de correccion de inconsistencias.
- El riesgo principal no es un unico fallo criptografico sino la suma de desalineaciones: headers, rutas, nombres de columnas, variables de entorno, servicios fuera del wrapper comun y diferencias entre migraciones, dump SQL y codigo.
- La verificacion puntual contra AWS RDS confirma que el esquema productivo real existe, pero tambien confirma drift material entre la DB viva y lo que varios servicios esperan en codigo.
- Los riesgos mas urgentes estan en: Auth/2FA, Gateway/CORS, resolucion de tenant por subdominio, Notifications service fuera del modelo zero-trust comun, AI service con autorizacion debil, y compatibilidad DB/codigo.

Nivel global estimado:
- Seguridad: ALTO
- Arquitectura/consistencia: ALTO
- Operabilidad: ALTO

4. FLUJO COMPLETO DE REQUEST
================================================================

Flujo nominal confirmado:
1. Frontend llama al gateway con Axios.
2. Axios envia:
   - `Authorization: Bearer <accessToken>` si hay token
   - cookies por `withCredentials: true`
3. Gateway aplica:
   - Helmet, compression, correlation ID, request ID
   - IP guard, DNS rebinding guard, subdomain resolver
   - CORS
   - body parsers + sanitizacion + HPP
   - content-type guard
   - cache headers
   - WAF
   - rate limiting
   - CSRF en `/api/${V}`
   - DLP
4. Gateway valida JWT/API key en rutas protegidas.
5. Gateway inyecta headers internos:
   - `X-User-Id`
   - `X-Org-Id`
   - `X-Branch-Id`
   - `X-User-Roles`
   - `X-User-Email`
   - `X-Request-Id`
   - `X-Trace-Id`
   - `X-Forwarded-For`
   - `X-Internal-Sig`
6. Microservicio valida `X-Internal-Sig` si usa `buildApp` o su propia proteccion.
7. Microservicio arma `req.user` desde headers.
8. Microservicio aplica RBAC y filtros DB.
9. MySQL/Redis responden.
10. Gateway devuelve JSON al frontend.

Headers clave usados:
- `Authorization`
- `Cookie: refreshToken=...` en refresh
- `X-API-Key`
- `X-Branch-Id`
- `X-Org-Id`
- `X-User-*`
- `X-Request-Id`
- `X-Trace-Id`
- `X-Internal-Sig`
- WebSocket: `Origin`, `Authorization` o `?token=`

Tokens usados:
- Access token JWT RS256
- Refresh token JWT RS256
- API keys hasheadas en DB
- HMAC interno `X-Internal-Sig`

Persistencia del lado cliente:
- Access token: `localStorage` key `accessToken`
- Legacy key aun leida: `andro_at`
- Usuario: `localStorage` key `andro_user`
- Refresh token: cookie httpOnly `refreshToken`

Cookies vs localStorage:
- Access token: localStorage
- Refresh token: cookie httpOnly
- El frontend usa un modelo hibrido, no 100% cookie-based

`credentials: include`:
- En Axios: SI, via `withCredentials: true`

Validacion de usuario:
- Primaria: gateway `gateway/src/middleware/auth.js`
- Secundaria en WS: `gateway/src/websocket.js`
- Microservicios comunes no validan JWT, confian en gateway + HMAC

Validacion de organizacion/tenant:
- JWT trae `orgId`
- gateway reinyecta `X-Org-Id`
- `tenantMismatchGuard` compara `req.user.orgId` con `req.tenantOrgId` si hay subdominio resuelto
- Muchos servicios filtran por `branchId`; algunos por `orgId`

Validacion de rol/permisos:
- Gateway protege rutas con JWT, pero el control de permisos finos ocurre mayormente en microservicios via `requirePerm()` / `guardWrite()`
- Excepcion importante: AI service usa un `requirePerm()` propio y muy debil

5. ESTADO DE AUTH
================================================================

Confirmado:
- Login con email/password + bcrypt
- JWT RS256 asimetrico en `shared/jwt.js`
- Refresh token rotation en `services/auth/src/controllers/auth.controller.js`
- Reuse detection de refresh via Redis `rt:used:*`
- Revocacion de access token por `revoked:<jti>` en Redis
- Cookie httpOnly para refresh token
- Logout y logoutAll
- Sesiones persistidas en tabla `sessions`
- Brute force en Redis + stored procedures DB
- JWKS publico en `/.well-known/jwks.json`

Problemas confirmados:
1. `logout`/`logoutAll` en auth service esperan `req.user.jti` desde header `x-jti`, pero el gateway NO reenvia `X-JTI`.
   Impacto:
   - Revocacion precisa del token actual puede no ejecutarse como se espera.
   - `logout` depende de DB `UPDATE sessions SET ... WHERE jti=:jti`, con `jti` potencialmente undefined.

2. Frontend 2FA roto:
   - Frontend envia `POST /auth/2fa/challenge` con `{ pendingToken, code }`
   - Backend valida `body('userId')` y `body('token')`
   - Controller espera `{ pendingToken, token }`
   Impacto:
   - El flujo 2FA no alinea request frontend/backend.
   - Riesgo operacional alto; posible bloqueo total de usuarios con 2FA.

3. `/auth/refresh`:
   - Backend acepta cookie o body `refreshToken`
   - Ruta publica en auth exige `body('refreshToken').notEmpty()`
   - Frontend llama `authApi.refresh()` con body `{}` y confia en cookie
   Impacto:
   - Puede romper por validacion express-validator antes de llegar al controller.

4. El frontend mezcla payload JWT y payload `user`:
   - Store calcula `orgId` desde `user.value?.org_id`
   - Login backend devuelve `user.orgId`
   - JWT trae `orgId`
   Impacto:
   - Estado de tenant inconsistente del lado cliente.

5. Comentarios/documentacion desalineados:
   - Gateway/OpenAPI mencionan JWT + refresh body.
   - Implementacion real usa cookie httpOnly para refresh.

Cookies:
- `refreshToken`
- `httpOnly: true`
- `sameSite: strict`
- `secure: true` solo en produccion
- Path: `/auth/refresh`

Riesgo auth global:
- ALTO

6. ESTADO DE CORS
================================================================

Configuracion real confirmada:
- Archivo: `gateway/src/middleware/cors.js`
- `credentials: true`
- Origins permitidos:
  - desarrollo: todos si `ALLOWED_ORIGINS` esta vacio o contiene `*`
  - produccion: `ALLOWED_ORIGINS` obligatorio y no puede ser `*`
- Headers permitidos:
  - `Content-Type`
  - `Authorization`
  - `X-API-Key`
  - `X-Branch-Id`
  - `X-Request-Id`

Problemas confirmados:
1. Faltan `X-Org-Id` y `X-Tenant-Id` en `allowedHeaders`.
   Impacto:
   - Si el frontend o un cliente browser los manda, el preflight puede fallar con:
     `Request header field x-org-id is not allowed by Access-Control-Allow-Headers`

2. Tampoco esta `X-CSRF-Token` en `allowedHeaders`.
   Impacto:
   - El gateway tiene endpoint `/csrf-token` y `csrfProtect`, pero el header esperado para mutaciones no esta permitido en CORS.

3. `ALLOWED_ORIGINS` vs `CORS_ORIGINS`:
   - Gateway usa `ALLOWED_ORIGINS`
   - `.env.production.example` define `CORS_ORIGINS`
   Impacto:
   - En produccion puede arrancar mal o bloquear trafico legitimo si solo se setea `CORS_ORIGINS`.

4. WebSocket usa tambien `ALLOWED_ORIGINS`, no `CORS_ORIGINS`.

Headers que deberian permitirse:
- `Authorization`
- `Content-Type`
- `X-Request-Id`
- `X-CSRF-Token`
- `X-Branch-Id`
- `X-Org-Id` si realmente se usa desde browser
- `X-Tenant-Id` solo si existe un caso de uso real de browser

Headers que sobran o son delicados:
- `X-API-Key` para browser no deberia ser la via principal si hay frontend publico
- `X-Org-Id` y `X-Tenant-Id` son peligrosos si el backend los considera fuente de verdad

Estado CORS:
- ALTO riesgo de desalineacion

6. `csrfProtect` aplicado globalmente a `/api/${V}`, pero el frontend no muestra manejo explicito de obtencion/envio de token CSRF.

9. PATIENTS ENDPOINT ESPECIFICO
================================================================

Endpoint auditado:
- `GET /api/v1/patients`
- `GET /api/v1/patients?page=1&limit=12`
- `GET /api/v1/patients?limit=1`

Ruta efectiva:
- Frontend -> gateway `/patients`
- gateway proxy -> patients service `/patients`

Validacion:
- Gateway OpenAPI:
  - `page` y `limit` documentados como string regex numerica
- Patients service OpenAPI:
  - `page` y `limit` documentados como integer
- Handler real:
  - `parseInt(req.query.limit || '20')`
  - `parseInt(page)`

Por que puede devolver 400 `Request validation failed`:
- Si la validacion activa que corre es la del servicio y no la del gateway, hay tension string vs integer.
- Los tests del repo muestran que el gateway fue adaptado para aceptar strings numericos en query.
- Si el validator del patients service no coercea y toma query string literal, puede rechazar `page=1&limit=12`.
- NO CONFIRMADO el comportamiento exacto en runtime sin ejecutar el stack completo, pero la desalineacion existe.

Por que puede devolver 500 `Internal server error`:
- Falta de tablas `patients`, `clients`, `patient_owners`
- Drift de columnas:
  - `chip_number` vs `microchip_number`
  - `birthdate` vs `date_of_birth`
  - `is_active` vs `active`
- Falta de `clients.branch_id` o `patients.organization_id`
- Falta de vistas/tablas secundarias (`species`, `breeds`, `coat_colors`)
- DB vacia pero con esquema incompleto

Sobre `page/limit`:
- Llegan como string desde query string
- El handler real los parsea manualmente
- El sistema depende de que la validacion OpenAPI no rechace esos strings antes

Si DB esta vacia:
- Con esquema correcto, deberia devolver 200 con array vacio y `total=0`
- No hay razon funcional para 500 solo por no tener registros

Observaciones de ownership/tenant:
- `GET /patients` filtra por `clients.branch_id` o por `patients.organization_id`
- `GET /patients/:id` filtra por `p.organization_id = :orgId`
- `POST /patients` NO inserta `organization_id` ni `branch_id` en `patients`
  Impacto:
  - Alta probabilidad de incompatibilidad con el esquema base que si incluye `organization_id` y otros campos
  - Riesgo de registros huerfanos o insercion fallida segun DB real

- razonable

Secrets:
- placeholders presentes
- inconsistencia de nombres alta

DB:
- mayor riesgo por drift de esquema

Redis:
- degradacion aceptable, pero abre huecos de enforcement

HTTPS:
- NO CONFIRMADO en runtime real
- HSTS configurado en app

WebSocket:
- valida origin y JWT
- broadcast por usuario existe
- no filtra por org/branch en broadcast global

Archivos:

Reportes:
- alto riesgo de fuga transversal si `orgId`/`branchId` fallan
